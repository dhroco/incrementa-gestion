La arquitectura de incrementa-gestion sobre Azure

Cómo queda el sistema cuando salga de Google Cloud: qué pieza de Azure reemplaza a cada una de hoy, cómo se conectan, quién puede entrar a qué, y en qué orden se migra. Todavía no hay nada construido en Azure, salvo el login de pre-prod.

Sale de las decisiones tomadas por David el 18 de octubre de 2026 (siete decisiones, una a la vez), contrastadas con el código de preprod en el commit 28ffc68 y con la rama david/texto-dinamico-base (1e30bdc), que agrega la revisión de redacción con Claude.
El inventario de Azure se midió ese mismo día con az ad app list, az ad user list, az billing account list y az account list --all.
El cambio futuro de las migraciones está en incrementa-azure-migraciones-bd-con-container-apps-job.html.
La lámina

Todo lo que habrá, en un solo dibujo

Los íconos no son los oficiales de Azure, sino círculos con una sigla. Azul es un servicio de Azure, blanco es un tercero y punteado es algo que todavía no se usa. El dibujo vale para los dos entornos: pre-prod y prod tienen las mismas piezas, cada uno en su suscripción y con su propio tenant de login.

Hay dos conexiones que no se dibujan para no tapar el resto. El backend valida cada token contra las claves públicas de Entra, y el navegador baja avatares, rúbricas y PDF directo de Blob Storage, con una URL temporal (SAS) que firma el backend.

Zona por zona

Qué hace cada bloque

Usuarios

El equipo de Incrementa entra con el navegador. Quien trabaja con el agente usa Claude, que habla con el MCP por HTTP. El MCP queda abierto como hoy en pre-prod, y el servidor HTTP abierto sigue negándose a arrancar con ENVIRONMENT=prod.

Identidad

Microsoft Entra ID, igual que hoy. Pre-prod usa el tenant de David (dvdrocogmail.onmicrosoft.com) y su app registration incrementa-gestion-dev. Prod usa el tenant de Incrementa, con una app registration propia que crea su administrador. El backend reconoce a cada persona por su email, así que los mismos datos sirven en los dos tenants.

Frontend

Static Web Apps sirve la aplicación compilada desde su CDN. Reemplaza al contenedor de nginx, que solo servía archivos. La URL del API se sigue fijando al compilar, como hoy. También permite definir cabeceras de seguridad, que hoy no hay.

Cómputo

Dos Container Apps en un mismo environment: el backend (Express) y el MCP, con la misma imagen y otro comando, igual que en Cloud Run. Escalan a cero, y cada uno tiene su propia identidad. Los dos corren con NODE_ENV=production, para que un error no devuelva el stack trace.

Red privada

El environment de Container Apps vive en una VNet. La base tiene un endpoint privado en esa red: el backend y el MCP la alcanzan sin pasar por internet. El firewall de la base solo deja entrar, desde fuera, la IP del Mac de David.

Base de datos

PostgreSQL 16 en Flexible Server, con TLS obligatorio. Pre-prod en un tier Burstable. Prod en General Purpose; si lleva alta disponibilidad se decide con el negocio. Las migraciones de Knex corren sin cambios. Al principio la clave de la base va en Key Vault.

Archivos

Una cuenta de Blob Storage con dos contenedores. documentos guarda los borradores, las rúbricas y los avatares. firmados guarda los PDF firmados, con una política WORM de 5 años, desbloqueada al inicio. Las rutas son las mismas que hoy en GCS: el servicio elige el contenedor según el prefijo, y la base no se toca. Soft delete y versionado en los dos.

Secretos e identidades

Un Key Vault por entorno, que Container Apps lee por referencia. id-backend e id-mcp tienen solo los permisos de su tarea. El backend pide su token de Graph con su identidad: desaparecen GRAPH_CLIENT_SECRET y la key JSON de GCS.

Entrega continua

GitHub Actions entra a Azure con OIDC federado, sin claves. Un registro de imágenes por entorno. El workflow de la app solo construye, publica y despliega. La infraestructura la cambia infra.yml, que muestra el what-if y espera la aprobación de David. Desplegar a prod también requiere su aprobación.

Terceros

No cambian con la migración: Microsoft Graph, Resend, la API de Claude (cuando se fusione la revisión de redacción) y Firme.cl, cuyo cliente está escrito pero todavía no se llama desde ningún lado.

Operación

Desde su Mac, David aplica el Bicep, carga los valores de los secretos y corre las migraciones, como hoy. El cambio futuro a un Container Apps Job está descrito en su propio documento.
