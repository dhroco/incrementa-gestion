Correr las migraciones de la base con un Container Apps Job

Un cambio para más adelante en incrementa-gestion, una vez que el sistema esté en Azure. Explica qué se cambia, por qué conviene, qué se gana y cómo se hace, paso a paso.

Estado: decidido para el futuro, no para la migración inicial. Al migrar a Azure, las migraciones se siguen corriendo como hoy, desde el Mac. Escrito el 18 de octubre de 2026.

1. Palabras que se usan en este documento

Base de datos
El lugar donde el sistema guarda sus datos: proveedores, clientes, plantillas y contratos. En Azure es un PostgreSQL Flexible Server.
Migración
Un archivo de código que cambia la forma de la base. Por ejemplo, agrega una tabla, agrega una columna o corrige el texto de una plantilla. Están en la carpeta backend/migrations/. Cada una se aplica una sola vez, en orden.
Aplicar las migraciones
Correr el comando knex migrate:latest. Ese comando revisa cuáles ya se aplicaron (lo anota en la tabla knex_migrations) y aplica las que faltan.
Imagen
Un paquete con el código del backend listo para correr. Se construye en cada despliegue y se guarda en el registro de imágenes (Azure Container Registry).
Container App
Un programa que corre siempre, esperando peticiones. El backend y el MCP son Container Apps.
Container Apps Job
Un programa que corre una vez, hace una tarea y termina. Usa una imagen, igual que un Container App, pero no queda encendido.
Red privada (VNet)
Una red dentro de Azure. Lo que está dentro se comunica sin pasar por internet. El backend, el MCP y la base están dentro.
Firewall de la base
La lista de direcciones de internet (IP) que pueden conectarse a la base desde fuera de la red privada.
Key Vault
El servicio de Azure que guarda los secretos, como la clave de la base.
Managed identity
Una identidad que Azure le da a un programa. Con ella el programa pide permisos sin usar claves.

2. Cómo se hace hoy

Hoy (y también justo después de migrar a Azure) las migraciones las aplica una persona, Ignacio, desde el Mac de David:

  1. Se abre una terminal en el Mac.
  2. Se cargan las variables con source ./set-env-local.sh. Ahí está la clave de la base.
  3. El Mac se conecta a la base. En GCP es con el Cloud SQL Auth Proxy. En Azure será directo, porque la IP del Mac está autorizada en el firewall.
  4. Se corre npm run migrate:latest dentro de backend/.
  5. Esto se hace antes de desplegar el código que necesita esa migración.

3. Cuál es el cambio

Se crea en Azure un Container Apps Job que se llama, por ejemplo, job-migraciones-preprod (y otro para prod). Ese job:

  • usa la misma imagen del backend que se va a desplegar;
  • corre dentro de la red privada, al lado de la base;
  • toma la clave de la base desde Key Vault;
  • ejecuta knex migrate:latest y termina;
  • se lanza a mano o desde el workflow de GitHub, después de que David lo aprueba.

Lo que no cambia: los archivos de migración, el comando de Knex, la tabla knex_migrations y la regla de que la migración va antes del código que la necesita.

4. Por qué se debe hacer

El modo de hoy funciona, pero tiene cinco problemas concretos:

Problema de hoyQué puede pasar
Depende de un computador. Solo se puede migrar desde el Mac de David.Si el Mac no está disponible, no se puede desplegar un cambio que necesite migración.
El código de la migración sale de la carpeta local.Se puede aplicar una migración de una rama que no es la que se despliega, o una versión distinta del archivo. La base queda distinta de lo que el código espera.
La base acepta conexiones desde una IP de internet.Hay que mantener esa IP en el firewall. Si la IP del Mac cambia, hay que actualizarla. Mientras está abierta, es una puerta más hacia la base.
El orden es manual. Una persona tiene que acordarse de migrar antes de desplegar.Si se olvida, el código nuevo llega a una base vieja y falla.
No queda un registro central.Para saber quién aplicó qué migración y cuándo, hay que preguntar o revisar una terminal.

5. Qué se gana

  • La migración y el código vienen de la misma imagen. Se aplica exactamente lo que se va a desplegar, del mismo commit.
  • Ya no depende del Mac. Cualquiera con permiso puede lanzarla desde GitHub o desde el portal de Azure.
  • El orden lo asegura el workflow. Primero el job; si falla, el despliegue se detiene y el código nuevo no sale.
  • Queda registro. Cada ejecución del job queda guardada en Azure con su fecha, su resultado y su salida, y en GitHub queda quién la aprobó.
  • Se puede cerrar el firewall. Cuando nadie necesite migrar desde fuera, se puede quitar la IP del Mac. La base queda accesible solo desde la red privada.
  • Costo casi cero. El job solo cobra los segundos que corre, normalmente menos de un minuto.

6. Cómo se hace, paso a paso

Se hace primero en pre-prod. Cuando funcione ahí, se repite en prod.

1

Crear una identidad para el job

Una managed identity propia, por ejemplo id-migraciones-preprod, con solo dos permisos:

  • Key Vault Secrets User en el Key Vault del entorno, para leer la clave de la base;
  • AcrPull en el registro de imágenes, para bajar la imagen del backend.

No necesita permisos sobre Blob Storage ni sobre Graph. Una identidad propia hace que el job no pueda hacer nada fuera de su tarea.

2

Agregar el job al Bicep del entorno

Se agrega un recurso Microsoft.App/jobs en el mismo environment de Container Apps del backend. Ejemplo de referencia (los nombres y versiones se ajustan al Bicep real):

resource jobMigraciones 'Microsoft.App/jobs@2024-03-01' = {
  name: 'job-migraciones-${entorno}'
  location: location
  identity: {
    type: 'UserAssigned'
    userAssignedIdentities: { '${idMigraciones.id}': {} }
  }
  properties: {
    environmentId: containerAppsEnv.id
    configuration: {
      triggerType: 'Manual'          // solo corre cuando se lanza
      replicaTimeout: 600            // máximo 10 minutos
      replicaRetryLimit: 0           // si falla, no reintenta solo
      manualTriggerConfig: { parallelism: 1, replicaCompletionCount: 1 }
      registries: [ { server: acr.properties.loginServer, identity: idMigraciones.id } ]
      secrets: [ {
        name: 'database-url'
        keyVaultUrl: '${keyVault.properties.vaultUri}secrets/DATABASE-URL'
        identity: idMigraciones.id
      } ]
    }
    template: {
      containers: [ {
        name: 'migraciones'
        image: '${acr.properties.loginServer}/backend:${imageTag}'
        command: [ 'sh', '-c' ]
        args: [ 'npx knex migrate:list && npx knex migrate:latest' ]
        env: [
          { name: 'ENVIRONMENT', value: envName }        // dev o prod
          { name: 'NODE_ENV', value: 'production' }
          { name: 'PGSSLMODE', value: 'require' }
          { name: 'DATABASE_URL', secretRef: 'database-url' }
        ]
        resources: { cpu: json('0.5'), memory: '1Gi' }
      } ]
    }
  }
}

Tres detalles de este ejemplo:

  • migrate:list se corre antes, para que la salida del job muestre qué migraciones estaban pendientes.
  • replicaRetryLimit: 0: una migración que falla no se debe reintentar sola. Una persona revisa por qué falló.
  • En Key Vault los nombres de secretos no aceptan _; por eso el secreto se llama DATABASE-URL.
3

Agregar un paso al workflow de GitHub

Va después de publicar la imagen y antes de desplegar el backend y el MCP. Se pone en un job aparte de GitHub con un environment que exige la aprobación de David:

migraciones:
  needs: build
  runs-on: ubuntu-latest
  environment: migraciones-preprod   # exige aprobación de David
  steps:
    - uses: azure/login@v2            # login OIDC, sin claves
      with:
        client-id: ${{ vars.AZURE_CLIENT_ID }}
        tenant-id: ${{ vars.AZURE_TENANT_ID }}
        subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
    - name: Aplicar migraciones
      run: |
        JOB=job-migraciones-preprod
        RG=rg-incrementa-preprod
        IMG="$ACR/backend:${{ github.sha }}"
        az containerapp job update -n $JOB -g $RG --image "$IMG"
        EXEC=$(az containerapp job start -n $JOB -g $RG --query name -o tsv)
        echo "Ejecución: $EXEC"
        for i in $(seq 1 60); do
          STATUS=$(az containerapp job execution show -n $JOB -g $RG \
                   --job-execution-name "$EXEC" --query properties.status -o tsv)
          echo "Estado: $STATUS"
          [ "$STATUS" = "Succeeded" ] && exit 0
          [ "$STATUS" = "Failed" ] && exit 1
          sleep 10
        done
        echo "::error::La migración no terminó a tiempo."; exit 1

deploy:
  needs: migraciones                  # el código sale solo si migrar salió bien
  ...

Si un despliegue no trae migraciones nuevas, el job corre igual, no encuentra nada pendiente y termina en segundos. No hace daño.

4

Probar en pre-prod

  1. Lanzar el job a mano una vez, sin migraciones pendientes. Debe terminar en Succeeded y mostrar la lista con todo aplicado.
  2. Preparar un cambio que traiga una migración nueva e inofensiva (por ejemplo, un índice) y desplegarlo por el workflow. Ver que el job la aplica antes del deploy.
  3. Probar el error a propósito: una migración que falla. El workflow se debe detener y el backend no se debe desplegar.
5

Actualizar las reglas del proyecto

  • CLAUDE.md: cambiar «las aplica el arquitecto contra pre-prod por el Cloud SQL Auth Proxy» por «las aplica el job de migraciones en el workflow, con aprobación de David».
  • .agent-orchestrator/perfil.yaml: no cambia. Las corridas de AOD siguen sin poder migrar; el job es el único camino.
  • Diseños de recortes (docs/disenos/prompts/*.md): donde dice «no la corras: la aplica Ignacio», pasa a decir «la aplica el job de migraciones al desplegar».
6

Repetir en prod y, si se quiere, cerrar el firewall

Crear job-migraciones-prod con su propia identidad y su environment de aprobación migraciones-prod. Cuando los dos entornos lleven un tiempo funcionando así, se puede quitar la IP del Mac del firewall de la base. Si alguna vez hace falta entrar a mano, se vuelve a agregar por un rato.

7. Cosas a cuidar

  • Las migraciones tienen que funcionar solas dentro de la imagen. La imagen no trae docs/ ni las pruebas (lo excluye .dockerignore). Una migración no puede leer archivos de esas carpetas. Las de plantillas ya cumplen esto: copian su texto dentro del archivo.
  • Revertir (migrate:rollback) no va en el workflow. Revertir puede borrar datos. Si hace falta, se lanza el job a mano, cambiando el comando solo para esa ejecución, y con decisión explícita de David.
  • Las semillas (seed:run) nunca se corren con este job.
  • Dos ejecuciones a la vez no se pisan. Knex usa la tabla knex_migrations_lock para que solo una aplique migraciones. Igual, el job está configurado para correr de a una.
  • Antes de una migración que reescribe datos (como las de plantillas), conviene un respaldo de la base. PostgreSQL Flexible Server tiene restauración a un punto en el tiempo, pero restaurar crea un servidor nuevo; lo más simple es seguir guardando respaldo en template_content_backup, como hoy.
